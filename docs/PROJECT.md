# НЕ ТАК — единый технический проект

Статус: проектирование. Сайт в GitHub Pages — демоверсия, не production. Дата: 2026-10-17.

## Цель
Превратить демонстрационный сайт веб-студии в управляемую систему: публичный сайт → расчёт → заявка → CRM → коммуникация → коммерческое предложение → проект → закрытие сделки.

## Подтверждено в текущем репозитории
- Статический одностраничный index.html с CSS/JS.
- Десять демонстрационных карточек портфолио, фильтры и модальные окна.
- Клиентский калькулятор, предварительные цены не утверждены.
- Форма только копирует бриф; отправки нет.
- Нет API, БД, CRM, чата, админки и интеграции Telegram в коде сайта.
- robots noindex,nofollow — сохранять до решения о запуске.
- Бренд и домен не утверждены; проверка обозначений NETAC/НЕ ТАК не завершена.

## Границы
НЕ ТАК — сайт и операционная система студии. Заглавная, ContextOS, Протокол 10/66, сайт психолога, StaffWay, WorkiJobs и другие — отдельные продукты/демонстрационные кейсы, не модули CRM студии.

## Персоны
1. Посетитель: просматривает услуги, кейсы, считает стоимость, оставляет заявку.
2. Менеджер: получает уведомление, ведёт лид, общается, отправляет КП.
3. Администратор: управляет пользователями, ценами, контентом, настройками.
4. Исполнитель (после MVP): задачи, файлы, сроки, статусы проекта.

## MVP — обязательные сценарии
1. Пользователь выбирает тип сайта, опции и видит ориентировочную стоимость.
2. Отправляет имя, контакт, описание, согласие; сервер валидирует данные.
3. API создаёт lead + immutable estimate snapshot + событие аудита в одной транзакции.
4. Telegram уведомляет менеджера; сбой доставки не теряет заявку, возможен повтор.
5. Менеджер авторизуется и видит список, детали, источник, смету и статусы.
6. Менеджер назначает ответственного, добавляет заметку, меняет этап.
7. Администратор редактирует тарифы и услуги с версионированием.
8. Клиент видит подтверждение с идентификатором обращения.
9. Администратор экспортирует/удаляет персональные данные согласно политике.
10. Мониторинг обнаруживает сбои API, очереди уведомлений и БД.

## Не включать в первый MVP
ИИ-чат, клиентский кабинет, платёжный шлюз, автоматическое формирование юридически значимых документов, многоуровневые права, WebSocket и Redis без реальной нагрузки. Включать после проверки спроса.

## Решения, требующие подтверждения
- Название и домен; правовая проверка.
- Канал связи: Telegram-бот, email, телефон; отдельный бот студии.
- Цены, пакеты, сроки и условия поддержки.
- Хостинг backend и БД, бюджет и юрисдикция хранения данных.
- Режим чата: человек, ИИ или гибрид.
- Набор юридических документов и требования к согласию.
- Какие кейсы можно показывать публично и какие материалы разрешены.

## Критерии готовности MVP
- Сквозной тест: браузер → API → БД → CRM → Telegram.
- При недоступности Telegram заявка остаётся в БД и повторно доставляется.
- Повторный POST с тем же idempotency key не создаёт дубликат.
- Никакие токены и персональные данные не попадают в клиентский bundle/логи.
- Неавторизованный доступ к CRM запрещён; роли проверяются сервером.
- Есть backup и успешно проверено восстановление.
- Доступность клавиатурой, mobile QA, ошибки форм, базовые показатели Web Vitals.
- Все юридические и коммерческие тексты утверждены до публикации.
